🗂️ 1. Collection Framework — Hiểu tận gốc

▶
HashMap Internal Mechanism
  • Dùng mảng Node[] table (default capacity 16)
  • Mỗi bucket là linked list; Java 8+: chuyển sang Red-Black Tree khi >8 nodes (tránh O(n) worst case)
  • hash = key.hashCode() ^ (key.hashCode() >>> 16)
  • index = hash & (capacity - 1)
  • Load factor mặc định = 0.75; resize khi vượt = capacity × load_factor
  • Key rule: nếu override equals() phải override hashCode()!
ConcurrentHashMap vs synchronized
  • Java 8: dùng CAS + synchronized trên từng bucket (segment removed)
  • Cho phép concurrent reads không block, writes chỉ lock bucket tương ứng
  • Không cho phép null key/value (khác HashMap)
  • computeIfAbsent(), merge() là atomic operations

⚡ 3. Concurrency — Thread Safety In Depth

▶

Visibility vs Atomicity

Vấn đề phổ biến nhất:
  • volatile: đảm bảo visibility (mọi thread đọc từ main memory) nhưng KHÔNG đảm bảo atomicity. i++ với volatile vẫn race condition!
  • synchronized: đảm bảo cả visibility lẫn atomicity, nhưng chậm hơn
  • AtomicInteger: dùng CAS (hardware atomic instruction) — nhanh hơn synchronized khi contention thấp

Deadlock — 4 điều kiện (Coffman)

  • Mutual Exclusion: resource không shared
  • Hold and Wait: giữ resource và chờ thêm
  • No Preemption: không thể force release
  • Circular Wait: T1→R1→T2→R2→T1
Tránh deadlock: luôn acquire locks theo thứ tự nhất quán, dùng tryLock(timeout), hoặc dùng higher-level abstractions.

ExecutorService Best Practices

// Tạo thread pool phù hợp: // CPU-bound tasks: Runtime.availableProcessors() ExecutorService cpuPool = Executors.newFixedThreadPool( Runtime.getRuntime().availableProcessors() ); // IO-bound tasks: nhiều hơn CPU count ExecutorService ioPool = Executors.newFixedThreadPool(50); // Luôn shutdown! try { cpuPool.shutdown(); if (!cpuPool.awaitTermination(60, TimeUnit.SECONDS)) { cpuPool.shutdownNow(); } } catch (InterruptedException e) { cpuPool.shutdownNow(); Thread.currentThread().interrupt(); }

CompletableFuture — Async Chain

CompletableFuture.supplyAsync(() -> fetchUser(id)) .thenApply(user -> enrichUserData(user)) .thenCompose(user -> fetchOrders(user.getId())) .exceptionally(ex -> handleError(ex)) .thenAccept(orders -> sendResponse(orders));

JVM Memory Areas

  • Heap: Young Gen (Eden + S0/S1) + Old Gen; GC hoạt động tại đây
  • Stack: mỗi thread có stack riêng; local vars + method calls

Bài 1: Pairs With Sum Target

MEDIUM HashMap · Array

📋 Mô tả bài toán

Cho một mảng số nguyên arr và số nguyên target. Hãy tìm tất cả các cặp chỉ số (i, j) thỏa mãn i < j và arr[i] + arr[j] == target. Mỗi cặp chỉ số được tính một lần. Trả về số lượng cặp tìm được.

📊 Ràng buộc

  • 1 ≤ arr.length ≤ 10⁵
  • -10⁶ ≤ arr[i] ≤ 10⁶
  • -2 × 10⁶ ≤ target ≤ 2 × 10⁶
  • Mảng có thể chứa phần tử trùng lặp

🔢 Ví dụ

Input
arr = [1, 5, 3, 3, 2, 4]
target = 6
Output
3
// Pairs: (1,5), (3,3), (2,4)
Input
arr = [1, 2, 3, 4]
target = 8
Output
0
// Không có cặp nào

⚡ Yêu cầu hiệu năng

Giải pháp O(n²) với brute force có thể pass nhưng sẽ bị chấm điểm thấp. Yêu cầu giải pháp O(n) time complexity và O(n) space complexity.

💡 Test Cases đặc biệt cần xử lý

  • Cặp tạo từ 2 phần tử giống nhau: [3, 3], target=6 → 1 cặp
  • Mảng toàn phần tử giống nhau: [2,2,2,2], target=4 → 6 cặp (C(4,2))
  • Phần tử âm: [-1, 1, -2, 2], target=0 → 2 cặp
🔍 Xem gợi ý tiếp cận
// Approach: HashMap One-Pass // Key: số cần để tạo thành target; Value: count // Với mỗi phần tử arr[i]: // - complement = target - arr[i] // - Nếu map.containsKey(arr[i]) → count += map.get(arr[i]) // - Sau đó map.merge(complement, 1, Integer::sum) public int countPairs(int[] arr, int target) { Map<Integer, Integer> freq = new HashMap<>(); int count = 0; for (int num : arr) { // Số cần để ghép với num = target - num int complement = target - num; // Nếu complement đã xuất hiện trước đó count += freq.getOrDefault(num, 0); // Lưu complement vào map để ghép với số sau freq.merge(complement, 1, Integer::sum); } return count; } // Time: O(n) · Space: O(n)

Bài 2: Longest Subarray with K Distinct

MEDIUM Sliding Window · HashMap

📋 Mô tả bài toán

Cho một mảng số nguyên arr và số nguyên k. Tìm độ dài của subarray liên tiếp dài nhất chứa đúng k giá trị phân biệt (distinct). Nếu không tồn tại, trả về 0.

📊 Ràng buộc

  • 1 ≤ arr.length ≤ 10⁵
  • 1 ≤ arr[i] ≤ 10⁵
  • 1 ≤ k ≤ arr.length

🔢 Ví dụ

Input
arr = [1, 2, 1, 2, 3]
k = 2
Output
4
// Subarray: [1,2,1,2]
// 2 distinct values: {1, 2}
Input
arr = [1, 2, 1, 3, 4]
k = 3
Output
3
// Subarray: [1,2,1] → NO, only 2
// Subarray: [1,3,4] hoặc [2,1,3] → length 3

⚡ Yêu cầu hiệu năng

Brute force O(n²) không đủ. Yêu cầu O(n) với Sliding Window technique.

💡 Lưu ý quan trọng

  • Đúng k distinct khác với tối đa k distinct — cần xử lý cẩn thận
  • Kỹ thuật: atMost(k) - atMost(k-1) để tính "đúng k"
  • Dùng HashMap để đếm tần số trong window
🔍 Xem gợi ý tiếp cận
// Trick: "exactly k" = "atMost(k)" - "atMost(k-1)" // atMost(k): tìm subarray dài nhất có TỐI ĐA k distinct public int longestSubarrayExactlyK(int[] arr, int k) { return atMost(arr, k) - atMost(arr, k - 1); } private int atMost(int[] arr, int k) { Map<Integer, Integer> freq = new HashMap<>(); int left = 0, maxLen = 0; for (int right = 0; right < arr.length; right++) { freq.merge(arr[right], 1, Integer::sum); // Thu nhỏ window khi distinct count > k while (freq.size() > k) { int leftVal = arr[left++]; freq.merge(leftVal, -1, Integer::sum); if (freq.get(leftVal) == 0) freq.remove(leftVal); } maxLen = Math.max(maxLen, right - left + 1); } return maxLen; } // Time: O(n) · Space: O(k)

Bài FT-1: Transaction Reconciliation

MEDIUM HashMap · Two-Pointer Payment

🎯 Bối cảnh Fintech

Vào cuối ngày, bộ phận Finance phải đối chiếu (reconcile) danh sách giao dịch từ Payment Gateway với Internal Ledger. Bất kỳ sự không khớp nào cũng là rủi ro tài chính nghiêm trọng.

📋 Mô tả bài toán

Cho hai danh sách giao dịch: gateway (từ bên thứ ba) và ledger (từ hệ thống nội bộ). Mỗi giao dịch có txId (String) và amountCents (long, đơn vị cent để tránh floating-point). Hãy tìm và phân loại ba trường hợp không khớp:

  • MISSING_INTERNAL: txId có trong gateway nhưng không có trong ledger
  • MISSING_GATEWAY: txId có trong ledger nhưng không có trong gateway
  • AMOUNT_MISMATCH: txId tồn tại ở cả hai nhưng số tiền khác nhau

📊 Ràng buộc

  • 0 ≤ gateway.size(), ledger.size() ≤ 10⁶ giao dịch
  • txId là chuỗi alphanumeric, unique trong mỗi danh sách
  • 0 ≤ amountCents ≤ 10¹² (long range an toàn)
  • Không được sort toàn bộ list (yêu cầu O(n) time)

🔢 Ví dụ

Gateway
TXN001 → 150000
TXN002 → 200000
TXN003 → 75000
TXN005 → 300000
Ledger
TXN001 → 150000
TXN002 → 199999  ← sai số tiền
TXN004 → 50000   ← extra
Output
MISSING_INTERNAL: [TXN003, TXN005]
MISSING_GATEWAY:  [TXN004]
AMOUNT_MISMATCH:  [TXN002]
  gateway=200000, ledger=199999

⚡ Yêu cầu hiệu năng

Với 10⁶ giao dịch, giải pháp O(n²) là không thể. Yêu cầu O(n + m) time và O(n + m) space.

💡 Edge cases quan trọng

  • Gateway rỗng hoặc Ledger rỗng → mọi item của bên kia là MISSING
  • Số tiền = 0 (refund đã hoàn tất) → vẫn cần match
  • Cùng txId xuất hiện nhiều lần trong một list → throw IllegalStateException (business rule)
  • Sử dụng long chứ không phải double để so sánh tiền tệ
🔍 Xem gợi ý tiếp cận
// ── Data classes ────────────────────────────────────────── public record Transaction(String txId, long amountCents) {} public record ReconciliationResult( List<String> missingInternal, // in gateway, not in ledger List<String> missingGateway, // in ledger, not in gateway List<String> amountMismatch // id present both sides, amount differs ) {} // ── Algorithm: O(n + m) với 2 HashMap ───────────────────── public ReconciliationResult reconcile( List<Transaction> gateway, List<Transaction> ledger) { // Build lookups — validate uniqueness Map<String, Long> gMap = buildMap(gateway); Map<String, Long> lMap = buildMap(ledger); List<String> missingInternal = new ArrayList<>(); List<String> missingGateway = new ArrayList<>(); List<String> mismatch = new ArrayList<>(); // Pass 1: check every gateway tx against ledger for (Map.Entry<String, Long> e : gMap.entrySet()) { String id = e.getKey(); if (!lMap.containsKey(id)) { missingInternal.add(id); } else if (!lMap.get(id).equals(e.getValue())) { mismatch.add(id); } } // Pass 2: ledger items not in gateway for (String id : lMap.keySet()) { if (!gMap.containsKey(id)) missingGateway.add(id); } return new ReconciliationResult(missingInternal, missingGateway, mismatch); } private Map<String, Long> buildMap(List<Transaction> list) { Map<String, Long> map = new HashMap<>(list.size() * 2); for (Transaction t : list) { if (map.put(t.txId(), t.amountCents()) != null) { throw new IllegalStateException("Duplicate txId: " + t.txId()); } } return map; } // Time: O(n + m) · Space: O(n + m) // NOTE: Dùng long, không dùng double cho so sánh tiền!

Bài FT-2: Velocity-Based Fraud Detection

MEDIUM Sliding Window · Deque Fraud Detection

🎯 Bối cảnh Fintech

"Card testing" là kỹ thuật fraud phổ biến: kẻ tấn công thực hiện nhiều giao dịch nhỏ liên tiếp để kiểm tra thẻ có hợp lệ không. Hệ thống phát hiện gian lận cần nhận diện pattern này real-time.

📋 Mô tả bài toán

Cho một stream sự kiện giao dịch events đã sort theo timestamp tăng dần. Mỗi event gồm (userId, timestamp, amountCents). Với mỗi user, kiểm tra liệu trong bất kỳ cửa sổ thời gian windowMs milliseconds nào có:

  • Số lượng giao dịch vượt ngưỡng txCountLimit, HOẶC
  • Tổng số tiền vượt ngưỡng amountLimit

Trả về Set<String> chứa userId bị flag là suspicious.

📊 Ràng buộc

  • 1 ≤ events.size() ≤ 5 × 10⁶
  • Timestamp đơn vị milliseconds, events sorted ascending
  • 1 ≤ windowMs ≤ 3,600,000 (tối đa 1 giờ)
  • 1 ≤ txCountLimit ≤ 100
  • 1 ≤ amountLimit ≤ 10¹²
  • Một khi user đã bị flag, bỏ qua các event tiếp theo của họ

🔢 Ví dụ

Input
windowMs = 60000 (1 phút)
txCountLimit = 3, amountLimit = 500000

events (userId, ts_ms, amount_cents):
user_A, 1000, 100000
user_B, 2000, 200000
user_A, 3000, 100000
user_A, 5000, 100000  ← user_A: 3 tx in 4s
user_B, 61000, 200000 ← user_B: tx 1 expired
user_A, 6000, 100000  ← 4th tx triggers count!
Output
Flagged: {"user_A"}

Giải thích:
- user_A: 4 tx trong 5s > txCountLimit=3
- user_B: chỉ có 1 tx trong mỗi cửa sổ 1 phút
  (tx thứ 2 tại 61s, tx thứ 1 tại 2s đã expired)

⚡ Yêu cầu hiệu năng

5 triệu events yêu cầu O(n) amortized. Không được dùng stream().sum() trong loop (O(n²) ẩn). Phải maintain running sum.

💡 Pitfalls thường gặp

  • Dùng stream().sum() trong loop → O(n²) ẩn → TLE
  • Quên maintain running sum khi pop từ deque
  • Cửa sổ có biên đóng: event tại ts - windowMs vẫn nằm trong cửa sổ
  • Một user bị flag sớm → skip event còn lại (tiết kiệm time)

// ── Data class ──────────────────────────────────────────── public record TxEvent(String userId, long timestamp, long amountCents) {} // ── Per-user sliding window state ───────────────────────── private static class UserWindow { Deque<long[]> window = new ArrayDeque<>(); // [timestamp, amount] long runningSum = 0L; void add(long ts, long amount) { window.addLast(new long[]{ts, amount}); runningSum += amount; } void evict(long cutoffTs) { // cutoff: ts - windowMs (inclusive boundary) while (!window.isEmpty() && window.peekFirst()[0] < cutoffTs) { runningSum -= window.pollFirst()[1]; } } } // ── Main algorithm: O(n) amortized ──────────────────────── public Set<String> detectFraud( List<TxEvent> events, long windowMs, int txCountLimit, long amountLimit) { Map<String, UserWindow> stateMap = new HashMap<>(); Set<String> flagged = new HashSet<>(); for (TxEvent e : events) { if (flagged.contains(e.userId())) continue; // skip already flagged UserWindow uw = stateMap.computeIfAbsent(e.userId(), k -> new UserWindow()); long cutoff = e.timestamp() - windowMs + 1; // closed window uw.evict(cutoff); uw.add(e.timestamp(), e.amountCents()); if (uw.window.size() > txCountLimit || uw.runningSum > amountLimit) { flagged.add(e.userId()); } } return flagged; } // Time: O(n) · Space: O(U × W) — U=users, W=max events/window

Bài FT-3: Best Currency Conversion Rate

MEDIUM Graph · DFS · BFS FX / Treasury

🎯 Bối cảnh Fintech

Treasury desk cần tìm tỷ giá chuyển đổi tốt nhất giữa hai đồng tiền, có thể qua nhiều bước trung gian (USD → EUR → JPY). Đây là bài toán Graph path optimization cổ điển trong FX.

📋 Mô tả bài toán

Cho danh sách tỷ giá trực tiếp (direct rates) giữa các cặp tiền tệ và một danh sách câu hỏi queries, với mỗi query [from, to] hãy tìm tỷ giá chuyển đổi tốt nhất (cao nhất). Tỷ giá có tính hai chiều: nếu USD→JPY = 150.0 thì JPY→USD = 1/150.0. Nếu không có đường đi → trả về -1.0.

📊 Ràng buộc

  • 1 ≤ số loại tiền tệ ≤ 100
  • 1 ≤ rates.length ≤ 1000 cặp direct rates
  • 1 ≤ queries.length ≤ 500
  • 0.0001 ≤ rate ≤ 10000.0
  • Không có arbitrage cycle nào trong input (đảm bảo consistency)
  • from == to → trả về 1.0

🔢 Ví dụ

Rates
USD → JPY = 150.5
EUR → USD = 1.08
GBP → EUR = 1.17
EUR → JPY = 162.5
Queries
[USD, JPY] → 150.5
[GBP, JPY] → 1.17×1.08×150.5 ≈ 190.2
[USD, GBP] → 1/(1.17×1.08) ≈ 0.792
[CNY, JPY] → -1.0 (không có đường)

⚡ Key Insight

Đây là bài "Evaluate Division" (LeetCode 399). Mỗi currency là node; mỗi rate là weighted edge hai chiều. Tìm đường đi từ src đến dst và nhân tích các weight dọc đường (DFS/BFS có visited set).

💡 Pitfalls thường gặp

  • Quên thêm inverse edge (JPY→USD = 1/150.5)
  • Không có visited set → infinite loop nếu có cycle
  • Dùng == so sánh String currency codes → phải dùng .equals()
  • Khi from == to nhưng currency không tồn tại trong graph → trả về -1.0, không phải 1.0
🔍 Xem gợi ý tiếp cận
// ── Build weighted bidirectional graph ──────────────────── public double[] findBestRates(double[][] ratesMatrix, String[] currencies, // [from, to] pairs String[][] queries) { // Step 1: Build adjacency map Map<String, Map<String, Double>> graph = new HashMap<>(); for (int i = 0; i < currencies.length; i += 2) { String from = currencies[i], to = currencies[i + 1]; double rate = ratesMatrix[i / 2][0]; graph.computeIfAbsent(from, k -> new HashMap<>()).put(to, rate); graph.computeIfAbsent(to, k -> new HashMap<>()).put(from, 1.0 / rate); } // Step 2: Answer each query with DFS double[] results = new double[queries.length]; for (int i = 0; i < queries.length; i++) { String src = queries[i][0], dst = queries[i][1]; if (!graph.containsKey(src) || !graph.containsKey(dst)) { results[i] = -1.0; } else { results[i] = dfs(graph, src, dst, new HashSet<>()); } } return results; } private double dfs(Map<String, Map<String, Double>> graph, String curr, String target, Set<String> visited) { if (curr.equals(target)) return 1.0; visited.add(curr); Map<String, Double> neighbors = graph.getOrDefault(curr, Map.of()); double best = -1.0; for (Map.Entry<String, Double> entry : neighbors.entrySet()) { if (!visited.contains(entry.getKey())) { double sub = dfs(graph, entry.getKey(), target, visited); if (sub > 0) best = Math.max(best, entry.getValue() * sub); } } visited.remove(curr); // backtrack — allow reuse in other queries return best; } // Time: O(Q × V × E) · Space: O(V + E) // ── BONUS: Precompute all pairs với Floyd-Warshall O(V³) ── // Nếu Q rất lớn, dùng Floyd-Warshall để precompute // dist[i][j] = best rate từ currency i đến j // dist[i][j] = max(dist[i][j], dist[i][k] * dist[k][j])

Bài FT-4: Loan Repayment với Compound Interest

MEDIUM BigDecimal · Simulation Lending / Credit

🎯 Bối cảnh Fintech

Hệ thống cho vay cần tính dư nợ chính xác sau một lịch trả nợ cụ thể. Floating-point sai số có thể dẫn đến tranh chấp pháp lý. Đây là lý do Fintech luôn dùng BigDecimal cho tính toán tiền tệ.

📋 Mô tả bài toán

Cho một khoản vay với principalCents (long), lãi suất hàng ngày dailyRateBps (basis points, 1 bps = 0.01%), và lịch trả nợ payments[][] (mỗi phần tử là [day, amountCents], sorted theo day tăng dần). Lãi được cộng gộp hàng ngày (compound daily). Tính dư nợ còn lại (tính đến cent) sau tất cả payments. Nếu dư nợ ≤ 0 → trả về 0.

📊 Ràng buộc

  • 1 ≤ principalCents ≤ 10¹² (tối đa 10 tỷ USD)
  • 1 ≤ dailyRateBps ≤ 100 (0.01% → 1% mỗi ngày)
  • 0 ≤ payments.length ≤ 10,000
  • 1 ≤ day ≤ 36,500 (tối đa 100 năm)
  • Ngày tính lãi: TRƯỚC khi nhận thanh toán trong ngày đó
  • Làm tròn: RoundingMode.HALF_UP (ngân hàng standard)

🔢 Ví dụ

Input
principal = 10,000,000 cents ($100,000)
dailyRateBps = 5 (0.05%/ngày)
payments:
  [30,  1,000,000]  ($10,000 ngày 30)
  [60,  1,000,000]  ($10,000 ngày 60)
  [90,  1,000,000]  ($10,000 ngày 90)
Output (approx)
Sau ngày 30:
  10M × (1.0005)^30 ≈ 10,151,322 cents
  Trừ 1,000,000 → 9,151,322

Sau ngày 60:
  9,151,322 × (1.0005)^30 ≈ 9,289,567
  Trừ 1,000,000 → 8,289,567

Sau ngày 90:
  8,289,567 × (1.0005)^30 ≈ 8,414,847
  Trừ 1,000,000 → 7,414,847

Result: 7,414,847 cents

💡 Tại sao KHÔNG dùng double?

  • 0.1 + 0.2 = 0.30000000000000004 trong double
  • Sau 365 lần nhân, sai số float tích lũy có thể lên đến vài nghìn cents
  • Fintech standard: BigDecimal với scale cố định và RoundingMode rõ ràng
  • Dùng BigDecimal.pow(int) để tính lũy thừa nguyên, tránh Math.pow(double,double)
🔍 Xem gợi ý tiếp cận
import java.math.BigDecimal; import java.math.MathContext; import java.math.RoundingMode; public long calculateRemainingBalance( long principalCents, int dailyRateBps, // basis points: 5 bps = 0.05% int[][] payments) { // [day, amountCents], sorted by day // 1 bps = 0.0001, so dailyRate = dailyRateBps / 10000 BigDecimal dailyRate = BigDecimal.valueOf(dailyRateBps) .divide(BigDecimal.valueOf(10_000), 10, RoundingMode.HALF_UP); BigDecimal multiplier = BigDecimal.ONE.add(dailyRate); // (1 + r) BigDecimal balance = BigDecimal.valueOf(principalCents); int currentDay = 0; for (int[] payment : payments) { int payDay = payment[0]; long payAmt = payment[1]; int days = payDay - currentDay; // Compound interest: balance × (1 + r)^days // BigDecimal.pow(int) is exact for integer exponents if (days > 0) { BigDecimal compoundFactor = multiplier.pow(days, new MathContext(20, RoundingMode.HALF_UP)); balance = balance.multiply(compoundFactor) .setScale(0, RoundingMode.HALF_UP); // round to cent } // Apply payment (interest accrues BEFORE payment on payDay) balance = balance.subtract(BigDecimal.valueOf(payAmt)); if (balance.compareTo(BigDecimal.ZERO) <= 0) return 0L; // fully paid currentDay = payDay; } return balance.setScale(0, RoundingMode.HALF_UP).longValue(); } // Time: O(p) — p = số lượng payments · Space: O(1) // NOTE: Không dùng double/float để nhân lãi suất! // BONUS: Dùng MathContext(20) để đảm bảo 20 chữ số có nghĩa trong // phép tính trung gian trước khi round về cent

Bài FT-5: Payment Batch Scheduling (Maximize Revenue)

MEDIUM-HARD Greedy · Union-Find Clearing House

🎯 Bối cảnh Fintech

Một Payment Clearing House nhận N batch thanh toán từ các ngân hàng thành viên. Mỗi batch có deadline (ngày cuối phải xử lý) và phí xử lý (revenue). Mỗi ngày chỉ xử lý được 1 batch. Hãy lên lịch để tối đa hóa tổng doanh thu.

📋 Mô tả bài toán

Cho mảng jobs[i] = [deadline, profit] với deadline là ngày cuối cùng (1-indexed) có thể xử lý batch. Bạn bắt đầu từ ngày 1. Tìm tổng profit tối đa khi chọn các job để xử lý (mỗi ngày tối đa 1 job, mỗi job tối đa 1 lần). Cũng trả về danh sách job index đã chọn.

📊 Ràng buộc

  • 1 ≤ jobs.length ≤ 10⁵
  • 1 ≤ deadline ≤ 10⁵
  • 1 ≤ profit ≤ 10⁹ (có thể overflow int → dùng long)
  • Yêu cầu output: max total profit và danh sách job index đã chọn
  • Nếu nhiều phương án cho profit bằng nhau, chọn cách nào cũng được

🔢 Ví dụ

Input
jobs = [
  [2, 500],   // Job 0: deadline d2, profit 500
  [1, 200],   // Job 1: deadline d1, profit 200
  [2, 300],   // Job 2: deadline d2, profit 300
  [3, 100],   // Job 3: deadline d3, profit 100
  [1, 400],   // Job 4: deadline d1, profit 400
]
Output
Max profit = 1000
Chọn: Job 4 (d1, +400)
       Job 0 (d2, +500)
       Job 3 (d3, +100)

Reasoning:
- Sort by profit: J0(500), J4(400), J2(300), J1(200), J3(100)
- J0: assign slot d2 → OK (1000 total: 500)
- J4: assign slot d1 → OK (total: 900)
- J2: deadline d2, slot d2 used → find d1? used → skip
- J1: deadline d1, slot d1 used → skip
- J3: deadline d3, assign d3 → OK (total: 1000)

⚡ Các approach

  • Naive O(n²): Sort by profit desc, try assigning từ deadline về ngày 1. Pass nhưng điểm thấp.
  • O(n log n) với Union-Find: Dùng disjoint set để tìm "slot trống gần deadline nhất" trong O(α(n)) ≈ O(1). Đây là optimal solution.
  • O(n log n) với PriorityQueue: Sort by deadline, dùng MinHeap size k — approach khác nhưng cùng complexity.

💡 Union-Find Insight

Mỗi slot (ngày) ban đầu trỏ về chính nó. Khi slot d bị dùng, ta set parent[d] = d-1. Gọi find(d) sẽ trả về slot trống gần nhất ≤ d (path compression). Nếu find(deadline) == 0 → không còn slot nào.

🔍 Xem gợi ý tiếp cận
// ── Approach 1: Greedy + Union-Find O(n log n) ─────────── public long[] schedulePaymentBatches(int[][] jobs) { int n = jobs.length; // Create index array to track original job indices Integer[] indices = IntStream.range(0, n).boxed().toArray(Integer[]::new); // Sort by profit descending (greedy: take highest profit first) Arrays.sort(indices, (a, b) -> jobs[b][1] - jobs[a][1]); int maxDeadline = Arrays.stream(jobs).mapToInt(j -> j[0]).max().orElse(0); // Union-Find: parent[d] = nearest available slot <= d int[] parent = new int[maxDeadline + 1]; for (int i = 0; i <= maxDeadline; i++) parent[i] = i; long totalProfit = 0; List<Integer> chosen = new ArrayList<>(); for (int idx : indices) { int deadline = jobs[idx][0]; int slot = find(parent, deadline); // nearest free slot <= deadline if (slot >= 1) { totalProfit += jobs[idx][1]; chosen.add(idx); parent[slot] = slot - 1; // mark slot as used → redirect to slot-1 } } System.out.println("Chosen jobs: " + chosen); return new long[]{totalProfit}; } // Path-compressed find — gần như O(1) per call private int find(int[] parent, int x) { if (parent[x] != x) parent[x] = find(parent, parent[x]); return parent[x]; } // Time: O(n log n) sort + O(n α(n)) UF ≈ O(n log n) · Space: O(maxDeadline) // ── Approach 2: Greedy + MinHeap O(n log k) ────────────── // Sort by deadline, maintain MinHeap of profits (size = current day) // Nếu job mới profit > heap.peek() → swap (take better job, free up slot) public long scheduleWithHeap(int[][] jobs) { Arrays.sort(jobs, Comparator.comparingInt(j -> j[0])); // sort by deadline PriorityQueue<Integer> minHeap = new PriorityQueue<>(); // min profit on top for (int[] job : jobs) { minHeap.offer(job[1]); if (minHeap.size() > job[0]) { // over capacity for this deadline minHeap.poll(); // remove the smallest profit job } } return minHeap.stream().mapToLong(Integer::longValue).sum(); } // Time: O(n log n) · Space: O(n) — cleaner code, same complexity

Inheritance & Method Overriding
Kế thừa và ghi đè phương thức — nền tảng OOP
⭐ Cốt lõi
Inheritance — Quy tắc
  • extends: một class chỉ extends được 1 class cha (single inheritance)
  • super(): phải là câu lệnh ĐẦU TIÊN trong constructor con
  • super.method(): gọi method của class cha từ class con
  • final class: không thể kế thừa (ví dụ: String, Integer)
  • final method: không thể override
  • protected: accessible từ subclass (kể cả package khác)
Method Overriding — Quy tắc
  • @Override: annotation compile-time check — rất quan trọng!
  • Cùng tên + tham số, return type cùng hoặc subtype (covariant)
  • Access modifier không được hẹp hơn cha (protected → public OK; public → private KHÔNG)
  • Exception checked chỉ được throw same hoặc subclass của cha
  • static method không override — chỉ hide (method hiding)
  • private method không override được
💻 Ví dụ — Inheritance + Runtime Polymorphism
class Animal { protected String name; Animal(String name) { this.name = name; } String speak() { return name + " nói gì đó..."; } final void breathe() { System.out.println("Thở..."); } // không thể override } class Dog extends Animal { private String breed; Dog(String name, String breed) { super(name); // GỌI CONSTRUCTOR CHA — PHẢI ĐẦU TIÊN this.breed = breed; } @Override String speak() { // override với @Override return super.speak() + " Gâu!"; // gọi method cha } @Override public String toString() { // override từ Object return "Dog{" + name + ", " + breed + "}"; } } class Cat extends Animal { Cat(String name) { super(name); } @Override String speak() { return name + " nói: Meo!"; } } // === RUNTIME POLYMORPHISM === Animal[] zoo = { new Dog("Rex", "Labrador"), new Cat("Kitty") }; for (Animal a : zoo) { System.out.println(a.speak()); // gọi đúng method của từng class // Output: "Rex nói gì đó... Gâu!" và "Kitty nói: Meo!" } // Compile-time type = Animal, runtime type = Dog/Cat Animal a = new Dog("Buddy", "Poodle"); a.speak(); // "Buddy nói gì đó... Gâu!" — Dog.speak() được gọi
⚠️ Bẫy phỏng vấn thường gặp: Nếu không có @Override, typo tên method sẽ tạo method mới (không override) — bug khó tìm. Luôn dùng @Override! Method hiding với static: Animal.staticMethod() gọi của Animal, Dog.staticMethod() gọi của Dog — không phải polymorphism.

Polymorphism — Overloading vs Overriding
Đa hình tại compile-time và runtime + instanceof & casting
⭐ Hay hỏi
Overloading — Compile-time Polymorphism
  • Cùng tên method, khác params (số lượng hoặc type)
  • Quyết định tại compile time dựa trên declared type
  • Return type, access modifier không liên quan
  • Nếu không match chính xác → auto-widening: int → long → float → double
  • Autoboxing sau widening: int → Integer chỉ khi không có overload nào khớp widening
instanceof & Casting
  • instanceof check tại runtime trước khi cast
  • Upcast (Dog → Animal): luôn an toàn, tự động
  • Downcast (Animal → Dog): cần explicit cast, có thể ném ClassCastException
  • Java 16+ Pattern Matching: if (a instanceof Dog d) — khai báo biến ngay, không cần cast thủ công
  • null instanceof X luôn trả về false — không ném NPE
💻 Ví dụ — Overloading, Casting, Pattern Matching
// === OVERLOADING === class Printer { void print(int x) { System.out.println("int: " + x); } void print(double x) { System.out.println("double: " + x); } void print(String x) { System.out.println("String: " + x); } } Printer p = new Printer(); p.print(5); // int: 5 (chính xác) p.print(5.0); // double: 5.0 p.print(5L); // double: 5.0 (widening: long → double) // === DOWNCASTING === Animal animal = new Dog("Rex", "Lab"); // Cách cũ (trước Java 16) if (animal instanceof Dog) { Dog dog = (Dog) animal; // explicit cast cần thiết dog.fetch(); } // Cách mới — Pattern Matching (Java 16+) if (animal instanceof Dog dog) { // khai báo 'dog' ngay trong instanceof! dog.fetch(); // 'dog' đã là Dog, không cần cast } // switch expression với pattern (Java 21) String sound = switch (animal) { case Dog d -> d.bark(); case Cat c -> c.purr(); default -> "unknown"; }; // ClassCastException nếu cast sai Animal cat = new Cat("Kitty"); // Dog dog = (Dog) cat; // Runtime: ClassCastException! // null instanceof Animal nullAnimal = null; System.out.println(nullAnimal instanceof Dog); // false — KHÔNG ném NPE
💡 Quy tắc vàng: Overloading = khi nào gọi (compile-time, static dispatch). Overriding = gọi gì (runtime, dynamic dispatch). Câu hỏi phỏng vấn phổ biến: "Kết quả khi gọi method bị overload với đối số null?" — Java chọn overload cụ thể nhất (most specific).

String — Immutability, Pool & StringBuilder
Hiểu sâu String để tránh bug và tối ưu performance
⭐ Hay hỏi
String Immutability & Pool
  • String immutable: mọi thao tác (toUpperCase, substring...) tạo String mới
  • String Pool (trong Heap): JVM tái sử dụng String literals có cùng giá trị
  • == so sánh reference; .equals() so sánh nội dung
  • new String("hello") tạo object MỚI trên heap, bypass pool
  • intern(): đưa String vào pool, trả về reference trong pool
  • Immutability → thread-safe by default, dùng làm HashMap key
StringBuilder vs StringBuffer vs String
  • String + trong loop: O(n²) — tạo n object mới!
  • StringBuilder: mutable, O(1) append, không thread-safe
  • StringBuffer: synchronized, thread-safe, chậm hơn StringBuilder
  • sb.append(x) trả về this → có thể chain
  • Java compiler tự optimize "a" + "b" + "c" → new StringBuilder().append("a").append("b").append("c")
  • Nhưng KHÔNG optimize trong loop → phải dùng StringBuilder tay
💻 Ví dụ — String Pool, == vs equals, StringBuilder
// STRING POOL String s1 = "hello"; // lưu vào String Pool String s2 = "hello"; // TÁI SỬ DỤNG từ Pool — cùng reference! Generics & Wildcards
Type safety at compile time · PECS principle · Bounded wildcards
Advanced
Generics Cơ Bản
  • Type erasure: generic types bị xóa tại runtime — List<String> ở runtime chỉ là List
  • Generic class: class Box<T> { T value; }
  • Generic method: <T> T identity(T x) { return x; }
  • Bounded type: <T extends Comparable<T>> — T phải là Comparable
  • Multiple bounds: <T extends A & B & C>
  • Không thể: new T(), new T[], instanceof T, static generic field
PECS — Producer Extends, Consumer Super
  • ? extends T (upper bound): đọc được, không ghi được — coi như Producer
  • ? super T (lower bound): ghi được, đọc về Object — coi như Consumer
  • ? (unbounded): không đọc, không ghi (ngoài null)
  • Ví dụ: copy(src: List<? extends T>, dst: List<? super T>)
  • Collections.sort() dùng Comparator<? super T>
  • Stream.filter() dùng Predicate<? super T>
💻 Ví dụ — Generic Method + Wildcards + PECS
// GENERIC CLASS class Pair<A, B> { final A first; final B second; Pair(A first, B second) { this.first = first; this.second = second; } static <X, Y> Pair<X, Y> of(X x, Y y) { return new Pair<>(x, y); } } Pair<String, Integer> p = Pair.of("Java", 17); // BOUNDED GENERIC METHOD public static <T extends Comparable<T>> T max(List<T> list) { return list.stream().max(Comparator.naturalOrder()).orElseThrow(); } max(List.of(3, 1, 4, 1, 5)); // 5 (Integer) max(List.of("Java", "Go")); // "Java" (String) // UPPER BOUND — Producer (đọc) void printNumbers(List<? extends Number> numbers) { for (Number n : numbers) { // OK — đọc được System.out.println(n); } // numbers.add(1.0); // COMPILE ERROR — không biết type chính xác! } printNumbers(List.of(1, 2, 3)); // List<Integer> OK printNumbers(List.of(1.0, 2.0)); // List<Double> OK // LOWER BOUND — Consumer (ghi) void addIntegers(List<? super Integer> list) { list.add(1); // OK list.add(2); // OK Object o = list.get(0); // chỉ đọc về Object } List<Number> numList = new ArrayList<>(); addIntegers(numList); // OK — Number là super của Integer // PECS — copy elements từ src sang dst public static <T> void copy(List<? extends T> src, List<? super T> dst) { for (T item : src) dst.add(item); } List<Integer> ints = List.of(1, 2, 3); List<Number> nums = new ArrayList<>(); copy(ints, nums); // ints produces, nums consumes
💡 Nhớ nhanh PECS: Khi bạn GET từ collection → dùng extends (Producer). Khi bạn PUT vào collection → dùng super (Consumer). Khi cả hai → dùng type parameter T cụ thể.

ArrayList vs LinkedList — Internal Structure
Khi nào dùng cái nào? Hiểu từ bên trong
⭐ Hay hỏi
ArrayList — Dynamic Array
  • Internal: Object[] elementData, default capacity = 10
  • get(i): O(1) — truy cập trực tiếp qua index
  • add(end): O(1) amortized — nếu full, grow 1.5x và copy
  • add(0, x): O(n) — shift toàn bộ phần tử sang phải
  • remove(i): O(n) — shift phần tử sau sang trái
  • Cache-friendly: contiguous memory → CPU cache hits tốt
  • Ít memory overhead hơn LinkedList
LinkedList — Doubly-Linked List
  • Internal: Node{prev, item, next} — mỗi node là 1 object riêng
  • get(i): O(n) — traverse từ đầu/cuối tới i
  • addFirst() / addLast(): O(1) — chỉ update head/tail pointer
  • removeFirst() / removeLast(): O(1)
  • Implements Deque: dùng được như Stack và Queue
  • Cache-hostile: nodes rải rác trong heap → nhiều cache miss
  • Memory overhead: mỗi element thêm 2 pointer (prev + next)
💻 Ví dụ — Khi nào dùng ArrayList, LinkedList, ArrayDeque
// === ARRAYLIST — Random access & iteration === List<Integer> list = new ArrayList<>(100); // đặt initial capacity tránh resize list.add(10); // O(1) list.add(20); list.get(0); // O(1) ✅ list.set(0, 99); // O(1) ✅ list.add(0, 5); // O(n) ❌ shift all Collections.sort(list); // O(n log n) — sort in-place // === LINKEDLIST — Queue / Deque operations === LinkedList<String> deque = new LinkedList<>(); deque.addFirst("A"); // O(1) ✅ — prepend deque.addLast("B"); // O(1) ✅ — append deque.peekFirst(); // O(1) ✅ — peek head deque.pollFirst(); // O(1) ✅ — remove head deque.get(50); // O(n) ❌ — sequential scan // === ARRAYDEQUE — tốt hơn LinkedList cho Stack/Queue === // Không có O(n) get, nhưng O(1) ở 2 đầu, cache-friendly Deque<Integer> stack = new ArrayDeque<>(); stack.push(1); stack.push(2); stack.push(3); stack.pop(); // 3 (LIFO) stack.peek(); // 2 Queue<Integer> queue = new ArrayDeque<>(); queue.offer(1); queue.offer(2); queue.poll(); // 1 (FIFO) // BENCHMARK NHỎ — hiểu tại sao // Thêm 1M elements vào đầu: // LinkedList.addFirst(): ~10ms (O(1) per op) // ArrayList.add(0, x): ~500ms (O(n) per op, shift many)
💡 Quy tắc thực tế: 95% trường hợp dùng ArrayList. Dùng LinkedList chỉ khi cần queue/deque operations ở cả 2 đầu. Thực ra ArrayDeque tốt hơn LinkedList cho hầu hết queue use cases (cache-friendly, ít GC pressure hơn).

HashMap — Cơ Chế Hoạt Động Bên Trong
Hash, bucket, collision, resize · equals() + hashCode() contract
⭐ Rất quan trọng
Cơ Chế put(key, value)
  • Bước 1: tính hash = key.hashCode() ^ (h >>> 16) — spread hash bits để giảm collision
  • Bước 2: tính index = hash & (capacity - 1) — capacity phải là power of 2 để dùng bit AND
  • Bước 3: nếu bucket trống → insert Node mới
  • Bước 4: collision → traverse linked list, so sánh bằng equals()
  • Bước 5: nếu size > capacity × 0.75 → resize: double capacity, rehash all
  • Java 8+: linked list > 8 nodes → chuyển thành Red-Black Tree → O(log n) thay O(n)
equals() & hashCode() Contract
  • Nếu a.equals(b) thì a.hashCode() == b.hashCode() — bắt buộc!
  • Ngược lại không cần đúng (cùng hash ≠ equals → collision)
  • Override một mình equals(): hai objects "bằng nhau" nhưng nằm 2 bucket khác nhau → HashMap bị lỗi
  • Override một mình hashCode(): get() tìm đúng bucket nhưng equals() false → không tìm thấy
  • Dùng Objects.hash(field1, field2) để tính hashCode
  • Lombok: @EqualsAndHashCode, IDE: auto-generate
💻 Ví dụ — HashMap đúng cách + equals/hashCode
// BUG: override equals() mà không override hashCode() class BadKey { int id; BadKey(int id) { this.id = id; } @Override public boolean equals(Object o) { return o instanceof BadKey bk && bk.id == this.id; } // THIẾU hashCode() → dùng Object.hashCode() → random hash! } Map<BadKey, String> map = new HashMap<>(); BadKey key1 = new BadKey(1); map.put(key1, "value"); BadKey key2 = new BadKey(1); // equals key1 nhưng hashCode khác! map.get(key2); // null — BUG! Không tìm thấy // ĐÚNG: override cả hai class GoodKey { int id; String name; GoodKey(int id, String name) { this.id = id; this.name = name; } @Override public boolean equals(Object o) { if (this == o) return true; if (!(o instanceof GoodKey)) return false; GoodKey k = (GoodKey) o; return id == k.id && Objects.equals(name, k.name); } @Override public int hashCode() { return Objects.hash(id, name); // dùng Objects.hash — dễ, đúng } } // USEFUL PATTERNS Map<String, Integer> freq = new HashMap<>(); // Đếm tần suất từ for (String word : words) { freq.merge(word, 1, Integer::sum); // atomic-style update // hoặc: freq.compute(word, (k, v) -> v == null ? 1 : v + 1); } // computeIfAbsent — khởi tạo giá trị mặc định Map<String, List<String>> groups = new HashMap<>(); groups.computeIfAbsent("fruits", k -> new ArrayList<>()).add("apple"); // getOrDefault — tránh null check int count = freq.getOrDefault("unknown", 0);
⚠️ Hiệu năng HashMap: Tránh dùng object lớn làm key (hashCode() tốn kém). Tránh hashCode() luôn trả về hằng số (mọi entry vào 1 bucket → O(n)). Set initial capacity khi biết trước size: new HashMap<>(expectedSize / 0.75 + 1)

TreeMap, PriorityQueue & Sorting
Comparable vs Comparator · Red-Black Tree · Min-Heap
Advanced
Comparable vs Comparator
  • Comparable: compareTo() — natural ordering trong class, thay đổi class gốc
  • Comparator: compare(a,b) — external ordering, linh hoạt, lambda
  • compareTo() convention: <0 (a<b), 0 (a==b), >0 (a>b)
  • TreeMap dùng compareTo() hoặc Comparator để sắp xếp key
  • Sắp xếp nhiều field: Comparator.comparing().thenComparing()
PriorityQueue — Min-Heap
  • Default: Min-Heap — phần tử nhỏ nhất ở đầu (peek/poll)
  • Max-Heap: new PriorityQueue<>(Comparator.reverseOrder())
  • offer(x): O(log n), poll(): O(log n), peek(): O(1)
  • Không đảm bảo thứ tự iteration — chỉ guaranteed là peek() là min
  • Phù hợp: scheduling, Dijkstra, K elements lớn/nhỏ nhất
💻 Ví dụ — TreeMap + Sorting + PriorityQueue
// COMPARABLE — natural ordering class Student implements Comparable<Student> { String name; int score; Student(String name, int score) { this.name = name; this.score = score; } @Override public int compareTo(Student o) { return Integer.compare(this.score, o.score); // tăng dần theo score } } // COMPARATOR — linh hoạt, nhiều criteria List<Student> students = new ArrayList<>(List.of( new Student("Alice", 90), new Student("Bob", 85), new Student("Carol", 90) )); // Sắp theo score giảm dần, cùng score thì theo tên tăng dần students.sort(Comparator.comparingInt(Student::getScore).reversed() .thenComparing(Student::getName)); // Alice(90), Carol(90), Bob(85) — nếu getScore và getName exist // TREEMAP — sorted by key TreeMap<String, Integer> scores = new TreeMap<>(); scores.put("banana", 2); scores.put("apple", 5); scores.put("cherry", 1); scores.firstKey(); // "apple" scores.lastKey(); // "cherry" scores.floorKey("avocado"); // "apple" (greatest key <= "avocado") scores.ceilingKey("avocado"); // "banana" scores.headMap("banana"); // {apple=5} scores.subMap("apple", "cherry"); // {apple=5, banana=2} // SẮP XẾP Map theo VALUE — hay hỏi trong phỏng vấn scores.entrySet().stream() .sorted(Map.Entry.comparingByValue(Comparator.reverseOrder())) .forEach(e -> System.out.println(e.getKey() + "=" + e.getValue())); // apple=5, banana=2, cherry=1 // PRIORITYQUEUE — tìm K phần tử nhỏ nhất int[] arr = {5, 1, 8, 3, 2, 7, 4}; PriorityQueue<Integer> minHeap = new PriorityQueue<>(Arrays.asList(arr)); // lấy 3 nhỏ nhất for (int i = 0; i < 3; i++) System.out.print(minHeap.poll() + " "); // 1 2 3
💡 Bài toán K-th largest element: Dùng Min-Heap size K: duyệt mảng, nếu element > heap.peek() → loại peek(), thêm element. Sau khi duyệt xong, peek() chính là K-th largest. O(n log k) thay O(n log n).

Concurrent Collections & Thread-Safe Patterns
ConcurrentHashMap · CopyOnWriteArrayList · BlockingQueue · Semaphore
Backend Critical
ConcurrentHashMap
  • Java 8: CAS + synchronized trên bucket (không lock toàn map)
  • Reads không cần lock trong hầu hết trường hợp
  • Writes lock chỉ bucket tương ứng → concurrent writes ở bucket khác OK
  • Không cho phép null key hoặc value (khác HashMap)
  • computeIfAbsent(), merge(), compute() là atomic
  • Dùng khi: nhiều thread read/write đồng thời (cache, session store)
CopyOnWriteArrayList
  • Mỗi write (add/remove/set) tạo bản copy mới của array
  • Reads hoàn toàn lock-free — đọc snapshot tại thời điểm read
  • Phù hợp: read-heavy, write-rare (event listeners, plugin list)
  • Write là O(n) — đắt, không phù hợp write nhiều
  • Iterator không ném ConcurrentModificationException
  • Snapshot semantics: iterator thấy data lúc iterator được tạo

⭐ Rất quan trọng
Intermediate Operations (Lazy)
  • KHÔNG chạy ngay — chỉ tạo pipeline description

  • map(Function): biến đổi 1-to-1

Tạo · Consume · Transform · Anti-patterns cần tránh
Best Practice
Tạo Optional
  • Optional.of(value): ném NPE nếu value là null
  • Optional.ofNullable(value): an toàn, wrap null thành empty
  • Optional.empty(): tạo empty Optional tường minh
Consume Optional
  • orElse(default): trả về default nếu empty — luôn evaluate
  • orElseGet(Supplier): lazy — chỉ gọi Supplier khi empty
  • orElseThrow(Supplier): ném exception nếu empty
  • ifPresent(Consumer): chỉ chạy nếu có value
  • ifPresentOrElse(Consumer, Runnable): Java 9+
Transform Optional
  • map(Function): biến đổi value → Optional<NewType>
  • flatMap(Function): khi mapper trả về Optional (tránh Optional<Optional>)

❌ Anti-patterns
  • Dùng get() không có check → bằng với null check thủ công
  • Optional làm field của class → overhead, serialization issues

Thread Lifecycle & Cách Tạo Thread
NEW → RUNNABLE → BLOCKED/WAITING → TERMINATED · Runnable vs Callable
⭐ Cốt lõi
6 Trạng Thái Thread
  • NEW: Thread object được tạo, chưa gọi start()
  • RUNNABLE: đang chạy hoặc sẵn sàng chạy (chờ CPU scheduler)
  • BLOCKED: chờ acquire synchronized lock đang bị thread khác giữ
  • WAITING: chờ vô thời hạn — wait(), join() không timeout
  • TIMED_WAITING: chờ có timeout — sleep(n), wait(n), join(n)
  • TERMINATED: run() hoàn thành hoặc ném exception
Runnable vs Callable vs Thread
  • Thread: extend class — không linh hoạt (Java chỉ đơn kế thừa)
  • Runnable: implement interface, run() → void, không throw checked exception
  • Callable<V>: call() → V, có thể throw Exception, dùng với ExecutorService
  • Daemon thread: t.setDaemon(true) trước start() — JVM exit khi chỉ còn daemon threads
  • join(): thread hiện tại chờ thread đó hoàn thành
  • interrupt(): set interrupt flag, không force stop

  • HikariCP DB pool: formula: (core_count × 2) + disk_spindles

Singleton — 3 cách thread-safe

SOLID Principles — Thiết Kế OOP Chuyên Nghiệp
Single Responsibility · Open/Closed · Liskov · Interface Segregation · Dependency Inversion
⭐ Phỏng vấn Senior
S — Single ResponsibilityMỗi class chỉ có 1 lý do để thay đổi. Class làm quá nhiều việc → khó test, khó maintain, khó reuse.
O — Open/ClosedMở rộng bằng cách THÊM code mới (implements interface mới), không SỬA code cũ. Plugin architecture.
L — Liskov SubstitutionSubclass phải có thể thay thế superclass mà không phá vỡ behavior. Nếu Bird.fly() nhưng Penguin không bay được → vi phạm LSP.
I — Interface SegregationNhiều interface nhỏ, chuyên biệt tốt hơn 1 interface lớn. Client không nên phụ thuộc vào methods nó không dùng.

1Q1 OOP Trong Java, khi Child extends Parent và cả hai định nghĩa static void foo(), gọi ((Parent) new Child()).foo() sẽ:
✅ Đáp án: B — Static method thuộc về class, không phải object. Java dùng method hiding — kiểu khai báo tại compile time quyết định, không phải runtime type.
1Q2 OOP Phát biểu nào về nguyên tắc Liskov Substitution (LSP) là SAI?
✅ Đáp án: C — LSP yêu cầu subtype không throw exception mới ngoài contract. Option A là đúng (preconditions phải bằng hoặc yếu hơn), B đúng (postconditions bằng hoặc mạnh hơn). C vi phạm contract, làm code client bị break.
1Q3 OOP Decorator pattern khác Inheritance ở điểm nào quan trọng nhất?
✅ Đáp án: B — Decorator dùng composition — wrap object gốc và delegate, thêm behavior linh hoạt tại runtime mà không vi phạm Open/Closed Principle. Inheritance cứng nhắc hơn ở compile time.
1Q4 OOP Rule nào áp dụng khi override method trong Java?
✅ Đáp án: C — Java: override method phải có visibility ≥ superclass method. Có thể mở rộng (protected → public) nhưng không thu hẹp (gây compile error). Đây là một phần của Liskov Substitution.
1Q5 Exception Trong try (A a = new A(); B b = new B()), nếu cả a.close() và b.close() throw exception:
✅ Đáp án: C — Resources đóng ngược thứ tự khai báo: b trước, a sau. Primary exception = b.close(). a.close() exception được attach vào primary qua addSuppressed(). Có thể lấy qua getSuppressed().
1Q6 Exception Cách xử lý nào là SAI khi bắt InterruptedException?
✅ Đáp án: C — Ignore InterruptedException là anti-pattern — nuốt interrupt signal, phá vỡ cơ chế shutdown/cancel. Luôn phải: restore interrupt flag (option A) hoặc rethrow (option D). Option B cho uncaught exception ở thread level.
1Q7 Exception @Transactional method ném IOException (checked), Spring sẽ:
✅ Đáp án: B — Spring mặc định rollback chỉ cho RuntimeException và Error. Với checked exception dùng @Transactional(rollbackFor = IOException.class). Đây là gotcha phổ biến gây data inconsistency.
1Q8 OOP Khi nào nên dùng abstract class thay vì interface?
✅ Đáp án: B — Abstract class: (1) state (fields), (2) constructors, (3) shared implementation — Template Method Pattern. Interface: capability contracts, multiple inheritance, API evolution với default methods.
1Q9 Basic Integer.valueOf(127) == Integer.valueOf(127) true, Integer.valueOf(200) == Integer.valueOf(200) false. Tại sao?
✅ Đáp án: B — JVM cache Integer [-128, 127]. Ngoài range này mỗi valueOf() tạo object mới. == so sánh reference → false. Dùng .equals() để so sánh value an toàn.
Q10 Basic Phát biểu đúng về Java pass-by-value:
✅ Đáp án: C — Java ALWAYS pass by value. Với object, value là bản copy của reference (địa chỉ). Vì vậy: modify object qua reference copy hoạt động; reassign reference trong method không ảnh hưởng caller.
Q11 Basic Output: String a=new String("x"); String b=new String("x"); — Kết quả của a==b, a.equals(b), a.intern()==b.intern()?
✅ Đáp án: B — a==b: false (hai heap objects khác). a.equals(b): true (nội dung giống). a.intern()==b.intern(): true (cùng String Pool reference sau intern).
Q12 Basic Performance issue khi String s=""+a+b+c trong loop 10K lần?
✅ Đáp án: B — String immutable — mỗi + tạo String mới. 10K lần × 3 concat = ~30K temporary objects. Dùng StringBuilder: 1 object, append(), toString() khi xong.

2Q1 Functional Stream lazy evaluation: intermediate operations chạy khi nào?

2Q2 Functional CompletableFuture.thenCompose() vs thenApply() — khác biệt?
✅ Đáp án: B — thenApply(f): nếu f trả CF<T> → kết quả là CF<CF<T>>. thenCompose(f): auto-flatten → CF<T>. Dùng thenCompose khi chaining async operations trả về future.
2Q3 Functional Phát biểu nào về Parallel Stream là SAI?
✅ Đáp án: B — Parallel stream có overhead của thread coordination. Không luôn nhanh hơn — cần: data lớn (≥10K elements), CPU-intensive ops, không I/O blocking. Với small dataset: sequential thường nhanh hơn.
2Q4 Functional f.andThen(g) vs g.compose(f) — thứ tự?
✅ Đáp án: A — f.andThen(g) = g(f(x)). g.compose(f) = g(f(x)). Cùng kết quả, khác cách viết: andThen là left-to-right (dễ đọc); compose là mathematical right-to-left.
2Q5 Algorithms Dijkstra với binary heap priority queue — total time complexity?
✅ Đáp án: B — E edges được relax: O(E). Mỗi relax push vào PQ: O(log V). Total: O(E log V). Dense graph (E≈V²): dùng array + linear scan cho O(V²) tốt hơn.
2Q6 Algorithms Phát hiện cycle trong directed graph — thuật toán tốt nhất?
✅ Đáp án: C — DFS 3-color: white=unvisited, gray=in DFS stack, black=done. Gặp gray node → back edge → cycle. O(V+E) time, O(V) space. Kahn's topological sort cũng detect cycle nhưng không trả path.
2Q7 Algorithms DP vs Greedy — khi nào cần DP hơn Greedy?
✅ Đáp án: B — Greedy đủ: local optimal = global optimal (Activity Selection, Huffman). DP cần: quyết định hiện tại ảnh hưởng nhiều future paths (0/1 Knapsack, LCS, Edit Distance).
2Q8 Algorithms Sliding Window Maximum (max mọi window k) — O(n) với structure nào?
✅ Đáp án: B — Monotonic deque decreasing: pop từ cuối nếu < element mới; pop từ đầu nếu out of window. Front = max hiện tại. Mỗi element push/pop đúng 1 lần → O(n) total.
2Q9 DS HashMap Java 8+: bucket treeify khi nào?
✅ Đáp án: A — Hai điều kiện: (1) bucket size > TREEIFY_THRESHOLD(8) VÀ (2) table capacity ≥ MIN_TREEIFY_CAPACITY(64). Nếu capacity < 64 → resize thay vì treeify.
Q10 DS HashMap.get() worst-case trước Java 8 treeification?
✅ Đáp án: C — Hash collision attack: tất cả keys cùng bucket → degenerate linked list → O(n) lookup. Java 8: treeify → O(log n) worst case. Java 8 cũng randomize hash để mitigate attack.
Q11 DS Thread-safe LRU Cache tốt nhất với Java collection?
✅ Đáp án: C — LinkedHashMap(accessOrder=true): tự maintain LRU order. Override removeEldestEntry() → auto-evict. Wrap với Collections.synchronizedMap() hoặc synchronized method cho thread safety.
Q12 DS ArrayDeque vs LinkedList làm Queue — lợi thế hiệu năng ArrayDeque?
✅ Đáp án: B — ArrayDeque: contiguous memory → CPU cache friendly. LinkedList: mỗi node object rải rác trong heap → cache miss mỗi pointer. ArrayDeque cũng tránh object allocation overhead của LinkedList node.

▼
📋 Đề bài: Sliding Window Rate Limiter
Skills: Algorithms · Data Structures · Code Optimization
Mô tả bài toán

Implement rate limiter cho N API requests từ nhiều clients. Mỗi client bị giới hạn maxRequests requests trong bất kỳ cửa sổ windowMs milliseconds nào (sliding window log algorithm). Xác định từng request: ALLOWED hay BLOCKED.

Input
  • int[][] requests — [clientId, timestamp] (ms)
  • int maxRequests — quota mỗi window
  • int windowMs — window size
  • Requests sorted by timestamp tăng dần
Output + Window
  • boolean[] — true=ALLOWED, false=BLOCKED
  • Window tại timestamp t: [t - windowMs + 1, t]
  • Chỉ đếm ALLOWED requests trong window
📌 Ví dụ
requests = [[1,0],[1,100],[1,200],[1,300],[2,150],[1,400]] maxRequests = 3, windowMs = 500 C1@t=0: window[-499,0], allowed_in_window=0 → count=1 → ALLOWED C1@t=100: window[-399,100], allowed={0} → count=2 → ALLOWED C1@t=200: window[-299,200], allowed={0,100} → count=3 → ALLOWED (đủ quota) C1@t=300: window[-199,300], allowed={0,100,200}→ count=3 đầy → BLOCKED C2@t=150: C2 window clear → count=1 → ALLOWED C1@t=400: window[-99,400], t=0 ngoài window, allowed={100,200} → count=2 → ALLOWED Output: [true, true, true, false, true, true]
💡 Solution: Per-client Sliding Window với ArrayDeque
☕ Java — O(N) amortized
import java.util.*; class RateLimiter { public boolean[] rateLimiter(int[][] requests, int maxRequests, int windowMs) { Map<Integer, Deque<Long>> windows = new HashMap<>(); boolean[] result = new boolean[requests.length]; for (int i = 0; i < requests.length; i++) { int clientId = requests[i][0]; long ts = requests[i][1]; long winStart = ts - windowMs + 1; // sliding window start Deque<Long> deque = windows.computeIfAbsent( clientId, k -> new ArrayDeque<>() ); // Expire timestamps trước window while (!deque.isEmpty() && deque.peekFirst() < winStart) deque.pollFirst(); if (deque.size() < maxRequests) { deque.addLast(ts); // ghi nhận allowed request result[i] = true; } else { result[i] = false; // quota exhausted — BLOCKED, không add } } return result; } }
Tại sao Deque?
  • peekFirst/pollFirst O(1) — expire old timestamps
  • addLast O(1) — append new timestamp
  • ArrayDeque cache-friendly (circular array)
  • O(N) amortized: mỗi timestamp add/remove đúng 1 lần
Key Design Decisions
  • BLOCKED requests không được add vào deque
  • computeIfAbsent: atomic + null-safe
  • long timestamp: ts có thể đến 10⁹ > int max
  • Per-client state: O(C × maxRequests) space
⚡ Complexity: O(N) amortized time · O(C×maxRequests) space

Task 5 Minimum Debt Settlement (Fintech Netting) ★★★ Hard — 45 phút
▼
📋 Đề bài: Minimum Debt Settlement (Fintech Netting)
Skills: Algorithms · Data Structures · System Design
Mô tả bài toán

N người có giao dịch lẫn nhau. Tìm số lượng transactions tối thiểu để settle tất cả nợ. Trong fintech: multilateral netting giảm 60-90% số settlement transactions so với bilateral netting.

Input
  • int N — số người (1 ≤ N ≤ 12)
  • int[][] transactions — [from, to, amount]
Output
  • int — min transactions để settle
  • Cho phép any-to-any payment
📌 Ví dụ
N=4, transactions=[[0,1,10],[1,2,5],[2,0,3],[3,1,4]] Net balance: P0=-7, P1=+9, P2=+2, P3=-4 Greedy settlement (3 transactions): P0 pays 7 → P1 | balances: [0, +2, +2, -4] P3 pays 2 → P1 | balances: [0, 0, +2, -2] P3 pays 2 → P2 | balances: [0, 0, 0, 0] ✓ Output: 3
💡 Solution: Net Balance + Greedy Matching (+ DFS Optimal)
☕ Java — Greedy O(N log N) + DFS optimal
import java.util.*; class DebtSettlement { // Greedy O(N log N) — practical cho production fintech public int minTransactions(int N, int[][] tx) { long[] bal = new long[N]; for (int[] t : tx) { bal[t[0]] -= t[2]; bal[t[1]] += t[2]; } List<Long> pos = new ArrayList<>(), neg = new ArrayList<>(); for (long b : bal) { if (b > 0) pos.add(b); else if (b < 0) neg.add(-b); } pos.sort(Collections.reverseOrder()); neg.sort(Collections.reverseOrder()); int count = 0, i = 0, j = 0; while (i < pos.size() && j < neg.size()) { long c = pos.get(i), d = neg.get(j); count++; if (c == d) { i++; j++; } else if (c > d) { pos.set(i, c-d); j++; } else { neg.set(j, d-c); i++; } } return count; } // DFS optimal — N≤12, xét tất cả cách settle public int minTransactionsDFS(int N, int[][] tx) { long[] bal = new long[N]; for (int[] t : tx) { bal[t[0]] -= t[2]; bal[t[1]] += t[2]; } List<Long> debts = new ArrayList<>(); for (long b : bal) if (b != 0) debts.add(b); return dfs(debts, 0); } private int dfs(List<Long> d, int s) { while (s < d.size() && d.get(s) == 0) s++; if (s == d.size()) return 0; long cur = d.get(s); int res = Integer.MAX_VALUE; for (int i = s+1; i < d.size(); i++) { long nxt = d.get(i); if (cur * nxt < 0) { // opposite signs: creditor↔debtor d.set(i, cur + nxt); res = Math.min(res, 1 + dfs(d, s+1)); d.set(i, nxt); // backtrack if (cur + nxt == 0) break; // perfect match: pruning } } return res; } }
Greedy Logic
  • Net balance = what actually needs settling
  • Match largest creditor với largest debtor
  • Mỗi iteration settle ít nhất 1 người hoàn toàn
  • Không always optimal nhưng rất tốt trong practice
DFS Optimal
  • Thử merge d[start] với mọi d[i] có opposite sign
  • Pruning: perfect match (sum=0) → stop branch
  • NP-hard general → exponential, OK cho N≤12
  • Fintech: N≤20 participants thường gặp
⚡ Complexity: Greedy O(N log N) · DFS O(N!) pruned — practical N≤12

✅ Đáp án: A — Oracle Sequence không đảm bảo tính liên tục (no-gap guarantee). Khi transaction rollback, sequence value đã consumed vẫn bị 'mất'. CACHE option (default CACHE 20) pre-allocate values → lost on instance restart. Đây là trade-off được chấp nhận để có performance. Sequence CÓ thể DESCENDING (INCREMENT BY -1).
1Q5 SQL/Oracle Phát biểu nào ĐÚNG về TRUNCATE vs DELETE trong Oracle?
✅ Đáp án: C — TRUNCATE: DDL, auto-commit, không rollback được, không fire row/statement triggers (kể cả BEFORE/AFTER DELETE), không ghi undo per-row (chỉ ghi deallocate extent info) → rất nhanh. DELETE: DML, ghi undo + redo per row, fire triggers, có thể WHERE, có thể rollback. Option D sai vì TRUNCATE không fire bất kỳ trigger DELETE nào.
1Q6 SQL/Oracle Trong Oracle, SYSDATE và CURRENT_DATE khác nhau như thế nào?
✅ Đáp án: B — SYSDATE: ngày giờ của database server OS (không aware timezone). CURRENT_DATE: ngày giờ theo session timezone (thay đổi theo ALTER SESSION SET TIME_ZONE). Trong ứng dụng đa timezone, dùng CURRENT_TIMESTAMP (với timezone info) hoặc SYSTIMESTAMP. Cả hai đều có cả date và time component.
1Q7 SQL/Oracle Tại sao Oracle documentation khuyến nghị dùng VARCHAR2 thay vì VARCHAR?
✅ Đáp án: C — Trong Oracle, '' (empty string) = NULL — khác SQL standard (empty string ≠ NULL). Oracle có thể trong tương lai thay VARCHAR để conform ANSI (empty string ≠ NULL), nhưng VARCHAR2 sẽ luôn giữ Oracle semantics. Để code an toàn với tương lai, dùng VARCHAR2. Cả VARCHAR và VARCHAR2 đều hỗ trợ Unicode với charset phù hợp.
1Q8 SQL/Oracle Oracle old-style outer join syntax: SELECT * FROM a, b WHERE a.id = b.a_id(+). Tương đương ANSI là?
✅ Đáp án: B — Dấu (+) đặt ở phía 'optional' table. b.a_id(+) → b là bảng optional (có thể NULL) → tất cả rows của a được giữ dù không match → LEFT OUTER JOIN. Ngược lại a.id(+) = b.a_id → RIGHT OUTER JOIN. Oracle old syntax không hỗ trợ FULL OUTER JOIN, phải dùng ANSI cho case đó.
1Q9 SQL/Oracle DUAL table trong Oracle được thiết kế để làm gì?
✅ Đáp án: C — DUAL là dummy table: 1 row (DUMMY='X'), 1 column. Dùng để evaluate expressions: SELECT 2*2 FROM DUAL, SELECT seq.NEXTVAL FROM DUAL, SELECT SYSDATE FROM DUAL, SELECT USER FROM DUAL. Trong Oracle 10g+, có thể SELECT mà không cần FROM DUAL trong nhiều contexts, nhưng DUAL vẫn cần cho compatibility.
Q10 SQL/Oracle DECODE(status, 'A', 'Active', 'I', 'Inactive', 'Unknown') tương đương CASE nào?
✅ Đáp án: B — DECODE(expr, val1, res1, val2, res2, ..., default) là Oracle-specific, tương đương Simple CASE. Quan trọng: DECODE coi NULL = NULL (hai NULL được coi là bằng nhau), còn CASE WHEN dùng = operator với NULL cho UNKNOWN. Để match NULL trong CASE cần viết CASE WHEN status IS NULL THEN ...
Q11 SQL/Oracle ROWID trong Oracle là gì và khi nào nên tránh dùng ROWID làm stable identifier?
✅ Đáp án: B — ROWID encode: data object number, file#, block#, row# within block. Fetch by ROWID = single precise I/O (nhanh nhất). Oracle index lưu ROWID để pointer từ index entry đến actual row. KHÔNG dùng ROWID làm stable identifier: thay đổi sau MOVE TABLE, SHRINK, EXPORT/IMPORT, partition operations. Extended ROWID (18 chars base-64) là format hiện tại.
Q12 SQL/Oracle Đoạn PL/SQL: SAVEPOINT sp1; UPDATE accounts SET bal=bal-100 WHERE id=1; ROLLBACK TO SAVEPOINT sp1; COMMIT;. Kết quả là?
✅ Đáp án: B — SAVEPOINT tạo checkpoint. ROLLBACK TO sp1 chỉ undo thay đổi SAU khi sp1 được tạo, không undo trước đó. Transaction vẫn tiếp tục active. COMMIT sau đó persist tất cả thay đổi trước SAVEPOINT sp1. Nếu muốn rollback toàn bộ: ROLLBACK (không có TO). SAVEPOINT có thể dùng nhiều lần trong một transaction.

2Q1 Analytic Fn Với dữ liệu scores: [100, 100, 90, 80]. ROW_NUMBER, RANK, DENSE_RANK trả về thứ tự cho 4 rows là?
✅ Đáp án: B — ROW_NUMBER(): luôn unique [1,2,3,4] (tie-breaking tùy ý). RANK(): tạo gaps — 2 rows cùng rank 1, row tiếp theo nhảy lên rank 3 (bỏ qua 2). DENSE_RANK(): không tạo gaps — 2 rows cùng rank 1, row tiếp theo là rank 2. Phổ biến trong báo cáo: RANK cho 'top N with ties', DENSE_RANK cho ranking liên tục.
2Q2 Analytic Fn LAG(amount, 1, 0) OVER (PARTITION BY account_id ORDER BY txn_date) trong phân tích giao dịch làm gì?
✅ Đáp án: B — LAG() nhìn về TRƯỚC (lag = trễ hơn, row trước). LEAD() nhìn về SAU. Tham số: LAG(column, offset=1, default=NULL). Offset 1 = row ngay trước. Default 0 khi không có row trước (đầu partition). PARTITION BY account_id đảm bảo không lấy row từ account khác. Dùng để tính: amount - LAG(amount) OVER (...) = month-over-month change.
2Q3 Analytic Fn LISTAGG(product_name, ', ') WITHIN GROUP (ORDER BY product_name) OVER (PARTITION BY order_id) dùng để:
✅ Đáp án: B — LISTAGG (Oracle 11gR2+): string aggregation. Aggregate mode (không OVER): collapse group thành 1 row. Analytic mode (với OVER PARTITION BY): giữ nguyên số rows, mỗi row thấy chuỗi concat của cả partition. Oracle 12.2+: LISTAGG(...) ON OVERFLOW TRUNCATE '...' INDICATORS để handle >4000 chars. 2Q4 Analytic Fn Trong Oracle hierarchical query: SELECT level, name FROM org CONNECT BY PRIOR id = manager_id START WITH manager_id IS NULL. PRIOR chỉ đến:
✅ Đáp án: B — CONNECT BY PRIOR: PRIOR chỉ đến giá trị ở row CHA. 'PRIOR id = manager_id' → id của row cha = manager_id của row con → traverse top-down (root → leaf). Đảo ngược: 'id = PRIOR manager_id' → bottom-up. START WITH xác định root rows. LEVEL pseudocolumn: 1=root, 2=child, etc. CONNECT_BY_ISLEAF: 1 nếu là leaf, SYS_CONNECT_BY_PATH cho full path string.
2Q5 Analytic Fn PIVOT operation trong Oracle SQL dùng để:
✅ Đáp án: A — PIVOT (Oracle 11g+): chuyển rows → columns. Ví dụ: từ (year, quarter, amount) → columns Q1/Q2/Q3/Q4 cho mỗi year. Phải biết trước các giá trị pivot (static). XML PIVOT cho dynamic columns. UNPIVOT: columns → rows (normalize). Tương đương viết CASE WHEN nhưng ngắn gọn hơn nhiều.
2Q6 Analytic Fn Oracle MERGE statement (UPSERT) trong một câu lệnh duy nhất cho phép:
✅ Đáp án: B — MERGE (SQL:2003 standard, Oracle 9i+): USING (source) ON (condition) WHEN MATCHED THEN UPDATE/DELETE WHEN NOT MATCHED THEN INSERT. Atomic, hiệu quả hơn: check-then-insert pattern. Oracle 10g thêm DELETE trong WHEN MATCHED. Một MERGE có thể có nhiều WHEN clauses. Phổ biến trong ETL, data sync, SCD (Slowly Changing Dimensions).
2Q7 Analytic Fn SUM(amount) OVER (PARTITION BY account_id ORDER BY txn_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) tính:
✅ Đáp án: B — ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW = running total. Frame variants: UNBOUNDED PRECEDING TO UNBOUNDED FOLLOWING = partition total. N PRECEDING TO CURRENT ROW = N+1 row moving sum. ROWS vs RANGE: ROWS dùng physical offset, RANGE dùng logical value range (handle ties khác nhau). Running total là use case phổ biến nhất trong fintech: account balance.
2Q8 Analytic Fn GROUP BY ROLLUP(dept, job) với 3 departments × 4 jobs tạo ra tổng bao nhiêu rows?
✅ Đáp án: C — ROLLUP(a,b) tạo: (a,b) detail groups + (a) subtotals + () grand total = N×M + N + 1. Với 3 dept × 4 jobs: 12 + 3 + 1 = 16 rows. CUBE(a,b) tạo thêm (b)-only subtotals: 12 + 3 + 4 + 1 = 20. GROUPING SETS cho phép chỉ định chính xác groupings. GROUPING() function trả về 1 nếu column là NULL vì rollup/cube (không phải NULL thật).
2Q9 Analytic Fn Ưu điểm chính của CTE (WITH clause) so với subquery thông thường trong Oracle SQL?
✅ Đáp án: B — CTE (Oracle 9i+, với WITH clause): (1) Readability — đặt tên cho logic phức tạp, (2) Reference nhiều lần trong cùng query (Oracle có thể inline hoặc materialize tùy optimizer), (3) Recursive queries (Oracle 11gR2+ theo SQL:1999 với UNION ALL). Oracle KHÔNG phải luôn materialize CTE — optimizer quyết định. Dùng MATERIALIZE hint để force.
Q10 Analytic Fn Sự khác biệt cốt lõi giữa GROUP BY và PARTITION BY (trong window function) là:
✅ Đáp án: A — GROUP BY: reduce dataset, không thể select non-aggregated columns. PARTITION BY (trong OVER clause): chia rows thành partitions để tính window function, nhưng KHÔNG reduce số rows — mỗi row vẫn có trong result với cả detail columns và calculated window value. Cho phép viết: SELECT name, salary, AVG(salary) OVER (PARTITION BY dept) as dept_avg — impossible với GROUP BY.
Q11 Analytic Fn LAST_VALUE(salary) OVER (PARTITION BY dept_id ORDER BY hire_date ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) trả về:
✅ Đáp án: A — LAST_VALUE với frame UNBOUNDED PRECEDING TO UNBOUNDED FOLLOWING → lấy value của row cuối cùng trong partition (person với hire_date cao nhất = được thuê gần đây nhất). Luôn explicit về frame khi dùng FIRST_VALUE/LAST_VALUE.
Q12 Analytic Fn Oracle recursive CTE (WITH...UNION ALL) khác CONNECT BY ở điểm nào quan trọng?
✅ Đáp án: B — Cả hai hỗ trợ hierarchical query. Recursive CTE (SQL standard): portable, dễ đọc hơn cho người quen SQL standard. CONNECT BY (Oracle-specific): CONNECT_BY_ISLEAF (leaf detection), SYS_CONNECT_BY_PATH (full path string), CONNECT_BY_ROOT (root value), NOCYCLE (cycle prevention keyword), ORDER SIBLINGS BY (sort within same level). Chọn CONNECT BY cho Oracle-only projects; Recursive CTE cho portability.

3Q1 PL/SQL Thứ tự ĐÚNG của các phần trong một PL/SQL named block (procedure/function) là:

3Q2 PL/SQL Ưu điểm của Cursor FOR Loop so với Explicit Cursor trong PL/SQL là:

3Q3 PL/SQL BULK COLLECT và FORALL trong PL/SQL giải quyết vấn đề gì?

Ứng dụng phổ biến: (1) Audit logging — log phải persist dù main TX rollback, (2) Trigger cần commit (trigger bình thường không thể COMMIT/ROLLBACK), (3) Error logging. 3Q6 PL/SQL Lợi ích chính của Oracle Package so với standalone procedures/functions?
✅ Đáp án: A — Package advantages: (1) Performance — loaded vào Shared Pool 1 lần cho session, subsequent calls reuse (vs standalone: mỗi call có thể cần load), (2) Encapsulation — private vs public, (3) Package-level variables — session-persistent state, (4) Overloading — nhiều procedures cùng tên khác signature, (5) Forward declarations, (6) Initialization block (BEGIN...END trong body). 3Q7 PL/SQL BEFORE INSERT trigger khác AFTER INSERT trigger ở điểm nào quan trọng nhất?
✅ Đáp án: B — BEFORE ROW trigger: fire trước khi data write. Có thể modify :NEW values (set default, uppercase name, generate PK từ sequence). RAISE exception → prevent INSERT. Dùng để: audit (log actual committed values), cascade updates to related tables, business logic cần final values.

4Q1 Performance Bitmap index phù hợp hơn B-Tree index trong trường hợp nào?
✅ Đáp án: B — Bitmap index lưu một bitmap per distinct value — hiệu quả cho low-cardinality (ít distinct values). DWH: AND/OR của nhiều bitmap cực nhanh, compact storage. TRÁNH bitmap trong OLTP: DML phải lock toàn bộ bitmap segment (không chỉ 1 row) → concurrency killer, deadlock risk. B-Tree: tốt cho high-cardinality, OLTP, range queries, index range scan. Function-based index: khi WHERE dùng function.
4Q2 Performance Trong EXPLAIN PLAN, operation = TABLE ACCESS FULL với large table nghĩa là gì và khi nào là vấn đề?
✅ Đáp án: B — TABLE ACCESS FULL = FTS — đọc mọi block trong segment. Cần xem xét khi: lấy <5-10% rows từ bảng lớn (missing/unused index), stale statistics, implicit type conversion disable index, function wrapping indexed column. Chấp nhận được: bảng nhỏ, query lấy phần lớn rows, data warehouse aggregate query. Dùng DBMS_XPLAN.DISPLAY_CURSOR để xem actual cardinality vs estimated — mismatch lớn = statistics vấn đề.
4Q3 Performance Function-Based Index (FBI) trong Oracle được tạo như thế nào và giải quyết vấn đề gì?
✅ Đáp án: A — FBI precompute và index kết quả của expression. Query PHẢI dùng exact expression: WHERE UPPER(name) = 'JOHN' → dùng FBI trên UPPER(name). WHERE name = 'JOHN' → không dùng FBI. Ứng dụng: case-insensitive search, computed columns, date truncation (TRUNC(order_date) = TRUNC(SYSDATE)). Oracle 11g+: virtual column tự động tạo cho FBI expression. Phải GATHER STATS sau tạo FBI.
4Q4 Performance Tại sao cần chạy DBMS_STATS.GATHER_TABLE_STATS định kỳ trong Oracle?
✅ Đáp án: B — Oracle CBO hoàn toàn phụ thuộc statistics: NUM_ROWS, AVG_ROW_LEN, NUM_DISTINCT, density, histograms, column correlations, system statistics (CPU, I/O speed). Stale stats → cardinality misestimate → wrong plan. Oracle 11g+ tự động gather stats trong maintenance window (DBMS_AUTO_TASK_ADMIN). Manually: GATHER_TABLE_STATS(schema, table, cascade=TRUE cho indexes). STALE_STATS column trong DBA_TABLES. Histogram quan trọng cho skewed data distributions.
4Q5 Performance Oracle Partition Pruning mang lại lợi ích gì?
✅ Đáp án: B — Partition pruning (partition elimination): optimizer xác định partitions cần thiết từ WHERE predicate trên partition key, chỉ đọc những partitions đó. Hiệu quả nhất với: range partition + date range WHERE, list partition + status IN WHERE. Static pruning: known at parse time. Dynamic pruning: determined at runtime (bind variables). Lợi ích: dramatically reduce I/O, parallel query efficiency, maintenance operations chỉ affect specific partitions.
4Q6 Performance Oracle optimizer hint /*+ INDEX(t idx_account) */ làm gì?
✅ Đáp án: B — Optimizer hints: gợi ý hoặc force execution strategy. /*+ INDEX(alias name) */ force use specific index. Các hints phổ biến: FULL (force FTS), NO_INDEX (disable index), USE_NL/USE_HASH (join method), PARALLEL (enable PQ), LEADING (join order), APPEND (direct path insert), RESULT_CACHE. Hints nên là last resort — thường là dấu hiệu cần fix statistics, rewrite query, hoặc add index. Stale hints nguy hiểm sau schema changes.
4Q7 Performance SELECT * FROM orders WHERE status='PENDING' FOR UPDATE NOWAIT trong Oracle làm gì?
✅ Đáp án: B — SELECT FOR UPDATE: acquire TX lock (row-level) trên rows. Các variants: FOR UPDATE (wait indefinitely), FOR UPDATE NOWAIT (fail immediately với ORA-00054), FOR UPDATE WAIT N (wait N seconds rồi fail). Dùng trong pessimistic locking patterns. Lock release khi COMMIT/ROLLBACK. FOR UPDATE OF column chỉ lock table có column đó (khi join nhiều tables). Tránh long-held locks trong OLTP — design để lock time ngắn.
4Q8 Performance Oracle Materialized View (MV) khác View thông thường ở điểm quan trọng nhất?
✅ Đáp án: B — View: query alias, mỗi lần query = re-execute underlying SQL. MV: snapshot lưu vật lý (như table), có thể refresh (COMPLETE = full rebuild, FAST = incremental via MV log, FORCE = try fast else complete). ON COMMIT refresh (realtime) hoặc ON DEMAND. Query Rewrite: Oracle tự redirect query từ base tables → MV nếu MV có answer. Ứng dụng DWH: pre-aggregate expensive calculations. DBMS_MVIEW.REFRESH.
4Q9 Performance Tại sao bind variables quan trọng hơn string literals trong Oracle OLTP applications?
✅ Đáp án: B — Oracle cache execution plan theo EXACT SQL text (case, spaces, literals). 'SELECT * FROM t WHERE id=1' và 'id=2' = 2 different SQL → 2 hard parses. Hàng nghìn unique queries/second = Library Cache thrash, high parse CPU, latch contention. Bind variables (:p1) → same SQL text → soft parse (just look up cached plan). Critical cho OLTP scalability: connection pool + bind vars = good. CURSOR_SHARING=FORCE là workaround nhưng không lý tưởng.
Q10 Performance Oracle Index Skip Scan xảy ra khi nào và hoạt động thế nào?
✅ Đáp án: B — Index Skip Scan: khi query thiếu leading column trong composite index nhưng leading column có FEW distinct values. Oracle logically splits index theo distinct values của leading column, thực hiện mini-scan trên từng sub-index. Hiệu quả khi: leading column cardinality thấp (vd: M/F, Y/N), query có selective predicate trên non-leading column. /*+ INDEX_SS(t idx_name) */ force. Không dùng khi leading column cardinality cao.
Q11 Performance Trong Oracle, vai trò của UNDO segments khi transaction ROLLBACK là:
✅ Đáp án: B — Oracle undo/redo duality: Undo lưu before-image (để rollback và read consistency). Redo lưu after-image (để crash recovery — re-apply committed changes). ROLLBACK process: read undo segments → generate compensating DML → restore before-image. Read consistency (MVCC): reader thấy consistent snapshot theo SCN — nếu block changed after reader's SCN, Oracle constructs consistent version từ undo. ORA-01555 'snapshot too old': undo overwritten trước khi query kết thúc.

Bối cảnh

Trong hệ thống ngân hàng, cơ cấu tổ chức theo dạng cây phân cấp. Mỗi nhân viên có thể là manager của nhiều người. Oracle giải quyết bài toán này bằng CONNECT BY PRIOR. Nhiệm vụ: implement tương đương trong Java.

Bài toán

Cho danh sách nhân viên int[][] employees, mỗi phần tử [empId, managerId, salary] với managerId = -1 là root (CEO). Tính tổng lương của toàn bộ subtree (bao gồm chính nhân viên đó) cho MỌI nhân viên. Trả về Map<Integer,Integer>.

Ví dụ
Input: [[1,-1,10000],[2,1,8000],[3,1,9000],[4,2,5000],[5,2,6000],[6,3,7000]]

Cây tổ chức:
  CEO (id=1, $10k)
  ├── Manager A (id=2, $8k)
  │   ├── Emp D (id=4, $5k)
  │   └── Emp E (id=5, $6k)
  └── Manager B (id=3, $9k)
      └── Emp F (id=6, $7k)

Output: {1=45000, 2=19000, 3=16000, 4=5000, 5=6000, 6=7000}
Giải thích: CEO = 10000+8000+9000+5000+6000+7000 = 45000
           Manager A = 8000+5000+6000 = 19000
Constraints
  • 1 <= employees.length <= 10,000
  • Đảm bảo là valid tree (no cycles, exactly 1 root)
  • salary range: [1, 1,000,000]
  • empId là unique positive integers
Oracle SQL tương đương
-- Oracle CONNECT BY equivalent:
SELECT e.emp_id,
       (SELECT SUM(s.salary)
        FROM employees s
        WHERE s.emp_id IN (
          SELECT emp_id FROM employees
          CONNECT BY PRIOR emp_id = manager_id
          START WITH emp_id = e.emp_id
        )) AS subtree_salary
FROM employees e;
Giải pháp Java — DFS Post-order
// Build children map + DFS post-order traversal
public Map<Integer,Integer> subtreeSalary(int[][] employees) {
    Map<Integer, List<Integer>> children = new HashMap<>();
    Map<Integer, Integer> salary = new HashMap<>();
    List<Integer> roots = new ArrayList<>();

    for (int[] emp : employees) {
        int id = emp[0], mgr = emp[1], sal = emp[2];
        salary.put(id, sal);
        if (mgr == -1) {
            roots.add(id);
        } else {
            children.computeIfAbsent(mgr, k -> new ArrayList<>()).add(id);
        }
    }

    Map<Integer, Integer> result = new HashMap<>();
    for (int root : roots) {
        dfs(root, children, salary, result);
    }
    return result;
}

private int dfs(int node,
              Map<Integer, List<Integer>> children,
              Map<Integer, Integer> salary,
              Map<Integer, Integer> result) {
    int total = salary.get(node);
    for (int child : children.getOrDefault(node, Collections.emptyList())) {
        total += dfs(child, children, salary, result);
    }
    result.put(node, total);
    return total;  // propagate subtree sum up to parent
}

// Iterative (tránh StackOverflow với cây rất sâu):
public Map<Integer,Integer> subtreeSalaryIterative(int[][] employees) {
    Map<Integer, List<Integer>> children = new HashMap<>();
    Map<Integer, Integer> salary = new HashMap<>();
    Map<Integer, Integer> result = new HashMap<>();
    List<Integer> roots = new ArrayList<>();

    for (int[] e : employees) {
        salary.put(e[0], e[2]);
        if (e[1] == -1) roots.add(e[0]);
        else children.computeIfAbsent(e[1], k -> new ArrayList<>()).add(e[0]);
    }
    // Topological BFS: process children before parents
    Deque<Integer> order = new ArrayDeque<>();
    Map<Integer, Integer> parent = new HashMap<>();
    for (int r : roots) {
        Deque<Integer> stack = new ArrayDeque<>();
        stack.push(r);
        while (!stack.isEmpty()) {
            int node = stack.pop();
            order.push(node);
            for (int c : children.getOrDefault(node, Collections.emptyList())) {
                parent.put(c, node); stack.push(c);
            }
        }
    }
    while (!order.isEmpty()) {
        int node = order.pop();
        int sub = result.getOrDefault(node, 0) + salary.get(node);
        result.put(node, sub);
        if (parent.containsKey(node))
            result.merge(parent.get(node), sub, Integer::sum);
    }
    return result;
}
Oracle CONNECT BY vs Java DFS
Oracle CONNECT BY: Built-in hierarchical traversal, concise SQL, nhưng N+1 correlated subquery approach O(N²). Dùng recursive CTE với cumulative SUM hiệu quả hơn.
Java DFS: O(N) time, O(N) space. Post-order traversal: xử lý lá trước, gộp kết quả lên cha. Iterative version tránh StackOverflowError với N=10,000 node chain.
Key insight: Bài toán này là "Tree Aggregation" — pattern phổ biến trong fintech: aggregate transactions up the account hierarchy, compute org-chart metrics.
⚡ Complexity: Time: O(N) — each node visited exactly once. Space: O(N) — children map + result map + DFS stack/queue. Iterative: avoids StackOverflow for deep linear chains (N=10000).
